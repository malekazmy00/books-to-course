## 2. التصميم

### 2.1 العقود (`b2c_contracts`، ‏SCHEMA 1.3.0، إضافة فقط)
- **`GateResult`**: قرار بوابة واحدة على artifact واحد: `gate_id`، و`gate_version`، و`kind` ‏(`deterministic|semantic|human`)، و`passed`، و`metrics`، و`evidence_ref`، و`decider` ‏(`system|human`)، و`decided_by`، و`decided_at` ‏(UTC).
  - البوابة البشرية لا يقررها إلا إنسان، والبوابة الآلية لا يقررها إنسان.
- **`ProducerIdentity`**: هوية نموذج أو prompt أو أداة.
- **`StageOutputRecord`**: الـ artifact، و`inputs`، و`code_revision`، و`config`، و`identities`، و`required_gates`، و`gate_results`، و`status`، و`status_reason`.
- **ثوابت العقد:**
  - `accepted` يتطلب وجود بوابة مطلوبة واحدة على الأقل، وأن تكون **آخر** نتيجة لكل بوابة مطلوبة ناجحة.
  - `accepted` يتطلب `code_revision` نظيفًا ومعروفًا: لا `unknown` ولا `-dirty`.
  - `rejected` و`quarantined` يتطلبان سببًا.
- **الانتقالات المسموحة** (`STAGE_OUTPUT_TRANSITIONS`):
  - `candidate → accepted | rejected`
  - `accepted → rejected` (سحب القبول فقط)
  - `rejected` نهائي، والإصلاح يُنتج artifact جديدًا
  - `quarantined → candidate` فقط: القديم يُعاد فحصه، ولا يُرقّى مباشرة

### 2.2 السجل (`b2c_core.stage_registry.StageOutputRegistry`)
ثلاثة جداول في قاعدة التطبيق:

| الجدول | المحتوى |
|---|---|
| `stage_outputs` | صف لكل artifact، مفتاحه `(course_id, stage, key)`: uri وsha256، و`inputs_json`، و`code_revision`، و`config_json`، و`identities_json`، و`required_gates`، والحالة وسببها ومن غيّرها |
| `stage_output_gates` | كل `GateResult` مُلحق، append-only. يُزال التكرار بالمحتوى (بصمة النتيجة دون الوقت)، فإعادة activity بالحكم نفسه لا تضيف صفًا |
| `stage_output_events` | كل تغيّر حالة: من، إلى، السبب، الفاعل، والـ revision الذي نفّذه. append-only |

- **append-only:** أي UPDATE أو DELETE على جدولي التاريخ يرفضه trigger في Postgres.
- **تغيير الحالة:** compare-and-set داخل transaction واحدة (`SELECT … FOR UPDATE`). تُبنى الحالة الجديدة عبر عقد `StageOutputRecord` قبل الكتابة، فلا يمكن أن يحمل الجدول صف `accepted` بلا بوابات ناجحة.
- **إنشاء الـ schema:** idempotent، مرة واحدة لكل instance، ومتسلسل بـ advisory lock.
- **الحالة في Postgres:** على نمط `translation_store`، لا في JSON تحت `_system/`.

### 2.3 واجهة الترقية (`b2c_orchestration.promotion.PromotionService`)
- `record_candidate(...)`: تسجيل idempotent كمرشح، مع البوابات المطلوبة والمدخلات والهويات والـ revision.
- `attach_gate(...)`: إلحاق نتيجة بوابة.
- `settle(...)`: يقرر حالة المرشح:
  - **رفض** إذا فشلت بوابة مطلوبة.
  - **انتظار** إذا بقيت بوابة بلا نتيجة (مثل بوابة بشرية).
  - **بقاء كمرشح** إذا كانت الصورة غير مختومة، مع تحذير في السجل.
  - **قبول** في غير ذلك.
- `promote` / `reject`: ترقية أو رفض صريح.
- `accepted_only(course, stage)` و`require_accepted(course, ref)`: المسار الوحيد الذي يقرأ منه المستهلك اللاحق.
- **`GatePolicy.version`:** يُشتق من تعريف الفحوص (sha256)، فلا يبقى إصدار قديم لقائمة فحوص تغيّرت (P2).

### 2.4 الربط بأحدث مسار: translate-book v2
- activity ‏`assemble_translation` تسجّل كل assembly مرشحًا. البيانات المسجلة:
  - المدخل: artifact ‏`translation-units`.
  - هويات المحركات المستخدمة.
  - الإعداد: `run_id` و`assembly_version` و`results_digest`.
  - `code_revision` للعامل.
- ثم تطبّق بوابة `translate-book.unit-decisions` (حتمية):
  - **القبول** فقط إذا كانت كل وحدة في الكتاب `accepted` أو `dropped`.
  - وحدة واحدة `needs_review` أو `rejected` أو بلا نتيجة ⇒ `rejected`.
  - بعد المراجعة البشرية تُنتج إعادة التجميع artifact جديدًا (المفتاح يتبع بصمة النتائج)، فيُفحص من جديد.
- `AssemblyResult` يحمل حقلًا اختياريًا جديدًا `status`.
- **لم يتغير تسلسل أوامر أي workflow** (التغيير داخل الـ activity فقط). اختبار `test_workflow_replay_safety` ناجح.

### 2.5 حجر المخرجات القديمة (`b2c_core.legacy_quarantine` + `scripts/quarantine-legacy-artifacts.py`)
- **المسح:**
  - عميل S3 للقراءة فقط (`ReadOnlyS3`): أي `put`/`delete` يرفع `PermissionError`.
  - يمر على الـ bucket كاملًا، ويقرأ manifests المراحل `build-outline` و`approve-outline` و`generate-course-qa` و`translate-content` و`translate-book` و`generate-mp3-track` و`generate-mp3` و`course-release`.
- **التسجيل:** كل artifact صالح يُسجَّل `quarantined` بسبب `legacy pre-gate` و`code_revision=unknown`.
  - الـ manifest الذي يخالف مساره يُبلَّغ عنه ولا يُسجَّل.
  - أي artifact له صف سابق يُترك كما هو، فتشغيل السكربت مرة ثانية لا يغيّر شيئًا.
- **الوضع الافتراضي dry-run:** لا اتصال بقاعدة البيانات أصلًا. `--apply` يكتب صفوف السجل فقط. لا يُكتب أي كائن ولا يُحذف.

### 2.6 الـ API
- **مسارات المشغّل (قراءة فقط، خلف رمز الـ API):**
  - `GET /v1/operator/stage-outputs?course_id=&stage=&status=&limit=&offset=`
  - `GET /v1/operator/stage-outputs/counts?course_id=`
  - `GET /v1/operator/stage-outputs/{course_id}/{stage}/{key}`: السجل، ونتائج البوابات، وتاريخ الحالة.
- **حارس المتعلم:** `deps.require_accepted_artifact(registry, course_id, ref)`.
  - يمر الـ artifact فقط إذا كان مقبولًا بالـ stage والـ key والـ uri والـ sha256 نفسها.
  - المرشح والمرفوض والمحجور وغير المسجل كلها **404 لا تُميَّز** عن بعضها.
  - تعطل السجل يعطي **503**، لا مرورًا مفتوحًا.
  - لم أعدّل مسارات المتعلم نفسها، لأن عاملًا آخر يعدّلها الآن لإخفاء الإجابات. الربط خطوة لاحقة صغيرة (§4).

### 2.7 إعادة الإنتاج (C3 / P8)
- **الـ Dockerfiles** (`api` و`worker` و`worker/Dockerfile.audio` و`worker/Dockerfile.recovery`):
  - `ARG B2C_GIT_REVISION`، و`LABEL org.opencontainers.image.revision`، و`ENV B2C_GIT_REVISION`.
  - توضع بعد طبقات الاعتماديات حتى لا يُبطل الـ revision الجديد الـ cache.
- **ملفات compose:** تمرر الـ build arg.
- **الـ Makefile:**
  - `make build` و`make up` يمرران `git rev-parse HEAD`.
  - يرفضان شجرة متسخة (تعديلات أو ملفات غير متتبعة، لأن `COPY` يضمّنها في الصورة) إلا مع `FORCE_DIRTY=1`، الذي يختم `<sha>-dirty`.
- **عند الإقلاع:** العامل وعامل الصوت والـ API يسجلون الـ revision. الحالة غير المختومة تُسجَّل كتحذير.

## 3. طريقة الاستخدام

**مرحلة جديدة تُنتج مخرجًا:**
```python
promo = PromotionService(StageOutputRegistry(settings.pg_dsn))   # code_revision من B2C_GIT_REVISION
promo.record_candidate(course_id, ref, required_gates=["my-stage.checks"], inputs=[parent_ref],
                       config={...}, identities=[ProducerIdentity(role="engine", model_id=..., prompt_version=...)])
promo.attach_gate(course_id, GateResult(stage=ref.stage, artifact=ref, gate_id="my-stage.checks",
                  gate_version=POLICY.version, kind="deterministic", passed=ok, metrics=m,
                  decider="system", decided_by="policy:my-stage.checks", decided_at=now))
promo.settle(course_id, ref)            # accepted | rejected | يبقى candidate
```

**مستهلك لاحق** (صوت، تصدير، تقديم): يقرأ عبر `promo.accepted_only(course, stage)`، أو يتحقق بـ `promo.require_accepted(course, ref)` (يرفع `NotAccepted`). مسارات الـ API تستخدم `require_accepted_artifact`.

**الحجر:**
```bash
uv run python scripts/quarantine-legacy-artifacts.py              # dry-run: تقرير JSON، بلا كتابة
uv run python scripts/quarantine-legacy-artifacts.py --apply      # يكتب صفوف quarantined (idempotent)
```

**المشغّل:** `GET /v1/operator/stage-outputs/counts?course_id=b2c-demo`.

## 4. ما يعمل الآن، وما يحتاج نشرًا بعد انتهاء الترجمات الجارية

| البند | الآن (في الفرع) | يحتاج نشرًا / قرارًا |
|---|---|---|
| العقود والسجل والترقية | مكتمل ومختبر | يُنشأ الـ schema تلقائيًا عند أول استخدام بعد النشر |
| ربط translate-book | مكتمل. replay-safe لأن الأوامر لم تتغير | إعادة بناء العامل من git (`make up`) **بعد** انتهاء الترجمات الجارية. بعدها كل assembly جديد يُسجَّل ويُقرَّر |
| الحجر | dry-run نُفذ على الـ bucket الحي (قراءة فقط) | تشغيل `--apply` داخل شبكة b2c بعد النشر وبموافقة المالك |
| مسارات المشغّل | مكتملة | تظهر بعد إعادة بناء الـ API |
| حارس المتعلم | الدالة واختبارها | ربطها بمسارات `/v1/released-*` والتصدير و`/saved-audio`، بعد دمج عمل إخفاء الإجابات. وجعل الصوت يقرأ الترجمة عبر `accepted_only` |
| ختم الصور | Dockerfiles وcompose وMakefile، ومختبر بـ `make -n` | أول `make up` من شجرة نظيفة. لاحقًا (P8): رفض الإقلاع لـ revision ليس في `main`، وبناء CI بالـ digest |

**تنبيه للنشر:**
- العامل الحالي يعمل بصورة غير مختومة. إن أُعيد بناؤه من شجرة متسخة بـ `FORCE_DIRTY=1`، ستبقى كل مخرجاته `candidate` ولن تُقبل. هذا مقصود.
- `docker/compose.qa-local.yml` ما زال ضمن ملفات `make up` الافتراضية، ويبني العامل من `Dockerfile.recovery` فوق `b2c-worker:dev`. ختمتُه حتى لا يظهر العامل `unknown`، لكن إزالة هذا الـ overlay (C3، §6.3) قرار مالك.

## 7. ما بقي مفتوحًا (R1 خارج هذا التسليم)

- **إطار `stage_activity` و`stage_identity` (P5/P6):** لم يُبنَ. السجل لا يكتب بعد في جداول `prov_*` في الـ transaction نفسها، ولا يوجد سجل `generation` لكل وحدة.
- **طابور المراجعة البشرية الموحد (P4):** لم يُبنَ. البوابات البشرية مدعومة في العقد فقط، ومعها authN للمراجعين.
- **باقي المراحل** (المخطط، والأسئلة، والصوت): لم تُربط بالترقية بعد. الصوت يجب أن يقرأ `accepted_only` من translate-book (R7).
- **رفض العامل للإقلاع** إن لم يكن الـ revision في `main`، وبناء CI للصور بالـ digest وSBOM، وإزالة صور الترقيع والـ overlays.
- **reconciler يومي** لـ registry parity (S3 ↔ `stage_outputs`).
- **ملاحظة جانبية وُجدت أثناء العمل:** `translation_store._UPSERT` يكتب عمود `termbase_digest`، لكن `_DDL` لا ينشئه. قاعدة جديدة فارغة ستفشل عند أول upsert. يبدو أن العمود أُضيف يدويًا في القاعدة الحية. **لم أصلحه** (خارج النطاق). يحتاج `ALTER TABLE … ADD COLUMN IF NOT EXISTS termbase_digest text NOT NULL DEFAULT ''`.
