Date: 2026-10-05

## Scope
The plan covers Arabic diacritization (CATT vs Sadeed), TTS provider evaluation, cloned-voice consent, audio assembly and MP3 quality gates, ASR and text/audio alignment. Provider choice remains an experiment (O-2).

## Implemented in this checkpoint
- Added a shared TTS provider protocol and validation for segment identity and nonempty result URI.
- Added fail-closed cloned-voice consent checks for scope, signature, effective time, and expiry. Built-in non-cloned styles do not require cloned-voice consent.
- Added deterministic checks for documented ACX limits: RMS -23 to -18 dBFS, peak <= -3 dBFS, noise floor <= -60 dBFS, 44.1 kHz, MP3, and 192 kbps CBR.
- Added comparison between stored AudioAsset measurements and independent probe measurements, plus segment ID/order/timing checks using the documented +/-100 ms bound.
- Added an isolated smoke runner for local TTS, MP3 assembly/probing, and a tiny local ASR check. Models and generated media are stored on the B2C data disk, not in the Git repository; no production runtime defaults or services were changed.

## Early direct-inference thread probe (not the production text path; superseded below) (2026-10-05)
- Environment: same Fasih CPU environment (Python 3.12.14, PyTorch 2.6.0+cpu), Intel Xeon E5-2658 v4 host (28 physical cores / 56 logical CPUs), 98 GiB RAM, CUDA unavailable. The official local checkout includes a CPU Dockerfile/server and uses shipped speaker latents; no missing GPU or reference-audio dependency was found. The earlier direct runner explicitly used intra-op/inter-op thread counts 28/8.
- Paired experiment used one loaded checkpoint and identical Arabic text, language, temperature 0.65, repetition penalty 2.0, disabled internal splitting, and reset Python/NumPy/PyTorch RNG to seed 1729 before each generation. Load used 4/4; inference was compared at 28/4 versus 4/4. Audio stayed 11.648 s in both runs. At 28 inference threads: 89.594 s, RTF 7.692. At 4 inference threads: 40.268 s, RTF 3.457 (2.23x faster in this paired run).
- Both clips were scored with `faster-whisper==1.2.1` / CTranslate2 4.8.2, `Systran/faster-whisper-tiny`, CPU/int8 (28 ASR threads), Arabic, beam 5, no VAD, no previous-text conditioning, and the same project Arabic normalization. Both yielded CER 14/106 = 13.21%; transcripts differed, but CER count and duration matched. Audio SHA-256: 28-thread `58769bff1c0ea3bf74ae3d1257e96270a5da3e07bdba37b8521b9f69bfe5ac9a`; 4-thread `604897201b308e2a876077f162a8dfd34fd834a5834a6c495348e1842cda161d`. Metrics and lossless WAVs are on the data disk under `/mnt/wsl/b2cdata/eval-datasets/speech/fasih-v1-cpu/paired-bench/`.
- This is one paired seed only. The earlier accepted exploratory Arabic clip had CER 3.77% but was a different unseeded generation, so it is not a valid paired quality baseline. A second repeat was interrupted by the owner’s request to finish; its 4-thread clip (41.427 s, 13.184 s audio, RTF 3.142) has no matching 28-thread result and is excluded. Exploratory 8/4/1-thread runs also varied in CER; they do not establish an acceptable quality floor.
- Decision: lower thread count is a promising CPU speed setting, and the paired sample showed no relative CER loss between 28 and 4 threads, but this evidence is too small to change a production default. Keep Fasih selected as the model, leave runtime settings unchanged, and retain a 3-paired-seed check as an open quality/latency gate. A persistent loaded process is important to amortize checkpoint startup. No quantization, compilation, batching, or model change was made because no quality-safe evidence was established for those options.


## Repeated full-text-path Fasih CPU benchmark (2026-10-05)
- Re-ran the official Fasih text path for three controlled seeds using the same plain Arabic text, model checkpoint, CATT text normalization/diacritization/chunking, language, sampling settings, and RNG reset before each generation. CATT produced two legal chunks of 104 and 110 characters (each below the XTTS Arabic 166-character limit); sampling was temperature 0.65, repetition penalty 2.0, internal XTTS splitting disabled. XTTS loaded once (37.112 s, Torch load threads 4/4); CATT loaded in 0.916 s; frontend preparation took 2.792 s. The model, CATT checkpoint, full run log, metrics, ASR results, and WAVs are on the data disk under /mnt/wsl/b2cdata/eval-datasets/speech/fasih-v1-cpu/catt-paired/; the checkpoint hash is recorded in metrics.json.
- Compared intra-op 28 vs 4 (inter-op fixed at 4) in one loaded model process. Per-seed inference seconds / audio seconds / inference RTF: seed1729: 291.937 / 13.973 / 20.892 vs 41.681 / 13.973 / 2.983; seed1730: 134.794 / 13.227 / 10.191 vs 40.285 / 13.227 / 3.046; seed1731: 136.912 / 13.269 / 10.318 vs 39.741 / 13.269 / 2.995. Paired 28-to-4 speedups were 7.004x, 3.346x, and 3.445x (median 3.445x). Mean inference was 187.881s at 28 threads and 40.569s at 4; mean inference RTF was 13.800 vs 3.008. Including the 2.792s text frontend, mean end-to-end was 190.673s/RTF14.007 vs 43.361s/RTF3.215.
- Tiny-ASR was run on all six clips with identical CPU/int8 Whisper Tiny, Arabic, beam 5, no VAD, no previous-text conditioning, and the same project normalization. Aggregate CER: 28 threads 17/318 = 5.35%; 4 threads 12/318 = 3.77%. Per seed (28 vs 4): 1729 5/106 vs 3/106; 1730 4/106 vs 3/106; 1731 8/106 vs 6/106. This is a small automatic intelligibility proxy, not human listening or a calibrated release threshold. All three 4-thread WAV hashes exactly match earlier full-CATT runs of the same seeds, supporting reproducibility for this path; the 28-thread outputs and ASR transcripts differ.
- The measured speed and CER favor 4/4 on this CPU. This does not prove human-perceived quality is better; it shows no degradation in this ASR proxy and a lower CER on these samples. The old 3.77% CER from a different unpaired direct-inference sample must not be used as a paired baseline.
- Startup dependency gap found and corrected only in the isolated evaluation environment: CATT needed pytorch-lightning and kaldialign plus its official checkpoint. They were installed/downloaded on the persistent data disk; no application image or production dependency set was modified. Fasih remains absent from the project runtime provider path, so there is no live service thread setting to inspect or deploy yet.
- Added a Fasih-scoped bootstrap helper at packages/speech/src/b2c_speech/tts/fasih_runtime.py. It defaults only Fasih to intra/inter-op 4/4, supports explicit B2C_FASIH_*_THREADS overrides, validates positive integer values, and has no import-time side effects. Unit tests use a fake Torch object; an isolated real-Torch check on 2.6.0+cpu verified get_num_threads()==4 and get_num_interop_threads()==4. The helper is not wired to a production provider, because no Fasih provider or deployable audio service exists in this repository yet; other Torch workloads are untouched. Call it once before model loading/parallel Torch work when the Fasih adapter is implemented.
- The benchmark concatenated the two chunk waveforms directly; the official server inserts a 120 ms inter-chunk gap. That gap does not affect model inference seconds and would add only 0.12 s to measured output duration. Production assembly must preserve the official gap.
- Official references: https://github.com/NightPrinceY/Fasih-TTS-V1 (CPU Dockerfile/server and shipped CATT pipeline); https://docs.pytorch.org/docs/stable/generated/torch.set_num_threads.html; https://docs.pytorch.org/docs/stable/notes/cpu_threading_torch.html. Fasih published quality/speed claims are author-reported and GPU-based; these local CPU results are separate evidence.
- Decision: keep Fasih selected for continued evaluation and use 4/4 as the provisional Fasih CPU-only setting when its worker is implemented. Do not change any running production configuration. CATT-path thread choice is now evidenced over three paired seeds, but Phase 8 remains NO-GO: no production provider/artifact persistence, no MP3 package pipeline, no calibrated ASR acceptance set or listening review, and no full speech-course gate.
